## Phase 2 feedback (on the modelling report)

| Feedback | What changed | Where |
|---|---|---|
| **Report CV scores with their fold-to-fold variation for the Problem 2 candidates** (Table 5 did not; Figure 1b did for the regression, Appendix F only for the selected model) | `src/selection_tables.py` lays out every candidate's score on each of the five expanding-window folds and the validation period (`report/results/cv_folds.csv`), with the mean, the population standard deviation (identical to the `cv_std` the results tables already carried — asserted by a test), range and test score. The Problem 2 results table now carries CV mean ± sd for every candidate; so does the regression table. A new figure draws every candidate on every window. Interpretation: the spread (±0.09) is a property of the windows and dwarfs the gap between the best candidates (< 0.001), which is the empirical case for the rank-based selection rule. The model card shows the same table and chart. | §7.3 (Table 5), Appendix G (Table 17, Figure 16), model card |
| **State the deployed Problem 2 model clearly and consistently; justify the choice** (§4.5 said the single boosted model could ship, Table 14 said Stacking, Appendix I said histogram-boosted variants) | The artifacts are the source of truth: `models/p2_lowreview.joblib` is the `StackingClassifier (A+B)` the pre-registered rank rule chose (mean rank 1.67 vs 2.00), with the tuned ℓ2 logistic regression and the tuned HistGradientBoosting classifier as members and a logistic meta-learner that weights the tree 13.8×. The single boosted model is within 0.001 PR-AUC; the stack is kept because the rule was fixed before any test score was seen and switching afterwards would be selecting on the test set. The README, the report's deployment section and the model card all say this, and `tests/test_leakage.py` now asserts that the pickles, `model_metadata.json`, `hyperparameters.csv`, the README and the report name the same estimators. The wrong statement in the Phase 2 Appendix I and README ("histogram-boosted variants") is removed. | §7.5, §8.1 (Table 7), README "What is deployed", model card "What is deployed", test section 9 |
| **Refer to Figure 3 in the text; the selected hyperparameter values were said to be in Appendix C but were not there** | Every figure in the final report is referred to from the body (checked by script before submission). `src/selection_tables.py` also writes `report/results/hyperparameters.csv` — the selected value of every searched model and the values carried by the deployed ensembles' members, read from the pickles — and Appendix D prints them (Table 11). The model card shows the same table. | Appendix D (Table 14), Appendix N (every figure referenced), model card |
| **§5.2's expected benefit assumes that contacting a customer prevents the low review; add this as a limitation and propose a pilot or A/B test** | Stated as its own limitation ("The benefit of outreach is assumed, not measured"). `src/pilot_design.py` sizes a randomised pilot: inside each day's top-K list, contact half at random, leave half; the control arm's rate is the model's precision at that daily K (0.572 at ten contacts); break-even is a 21.9 % relative reduction (one averted review in five); detecting a one-in-four reduction at 80 % power needs 191 orders per arm, about six weeks at ten contacts a day. The model card carries a calculator for any capacity, effect and power. | §9.4, §10, Appendix L (Table 23, Figure 24), model card "Sizing the outreach pilot" |
