\section{Model Deployment and Application}
\label{sec:deployment}

The proof of concept is a Streamlit application deployed on Streamlit
Community Cloud at \url{https://team10-it5006-olist.streamlit.app}, built from
the \code{deployment/} folder of the repository. It serves all three deployed
models, and because the Olist extract ends in 2018 it does what the brief
anticipates: it predicts on held-out historical records that stand in for new
orders, and it can replay the test window a day at a time.

Nothing in the application reimplements the training-time feature engineering:
a form submission or an uploaded row is pushed through the same
\code{src/features.py} builders the models were fitted on, so no feature is
computed one way in training and another in production \citep{sculley2015debt}.
A seller's track record, which a form cannot supply, comes from
\code{models/history\_lookup.csv} at each level of the training code's fallback
chain. The artifacts total under 1\,MB, record the \code{scikit-learn} version
that wrote them (pinned in \code{requirements.txt}; the loader warns if it
drifts) and are loaded once per server process.

\subsection{What the application does}

The application has nine tabs (Figures~\ref{fig:app-journey} to
\ref{fig:app-card}) and opens on the customer. \textbf{Customer journey} follows
any reviewed test order --- by default the order of Box~1 --- from checkout to
review: what the customer went through, what each deployed model said at that
moment, which contact could still have reached them, and their own words. Five
tabs are the exploratory analysis of Section~\ref{sec:eda}, four with filters.
\textbf{Predict} (Figure~\ref{fig:app-predict}) scores an order entered as it
would look at checkout --- the expected lead time with its typical error, the
date the customer would be quoted (forecast plus the margin), the risk of
missing the promise and the conditional low-review risk --- and turns an
uploaded CSV of up to 5{,}000 orders into a \textbf{triage list} with the
top-$K$ marked. \textbf{Replay a day}
(Figure~\ref{fig:app-replay}) ranks the held-out orders of any test day blind, by
purchase or delivery day, then reveals what each customer went through; for 16
July 2018 at ten contacts, eight of the ten went on to rate 1--2 stars, four
still waiting for a late parcel and four whose order never came, so a call at
delivery could have reached none of them before they wrote and a message on the
promised date all eight. \textbf{Model card} states what is deployed as read from
the artifacts (Table~\ref{tab:deployed}), the protocol, the selected
hyperparameters, the fold-to-fold variation, where the models should not be
trusted \citep{mitchell2019modelcards}, and a calculator for both pilot arms with
the costs as inputs; every figure on it is labelled observed, assumed, derived
or planned. The application refits nothing: every figure is read from the result
tables or computed from the saved test predictions, and
Appendix~\ref{app:figures} gives a five-step guide to using it.

\subsection{Robustness, reachability and reproducibility}

Invalid input --- a promised date before the purchase, a non-positive price,
more sellers than items, a malformed, empty or oversized upload, a missing
column, an unknown category or state, a missing artifact or a version mismatch
--- produces a specific message rather than a traceback, and the data loader
stops the app if the row count of any source table changes. There are no API
endpoints and no credentials: the batch CSV contract in
\code{deployment/README.md} is the programmatic surface.

The Phase 1 dashboard went down with the suspended GitHub account it was
deployed from. The application now deploys from the team's current repository;
the README records what keeps it reachable (Community Cloud's one-click wake-up
after twelve idle hours; Python 3.12 in the app's settings), and a fresh clone
reproduces every table, figure and number here (Appendix~\ref{app:repro}).
